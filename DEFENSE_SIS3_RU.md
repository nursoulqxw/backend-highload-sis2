# Шпаргалка к защите SIS #3 (тюнинг базы)

Полный отчёт с цифрами: [SIS3.md](SIS3.md). Здесь — то же самое коротко и по-русски.

## Речь на 2 минуты

> **Задача:** сделать базу быстрее под нашу нагрузку и доказать это цифрами.
>
> **Данные:** 50 млн постов и 20 млн лайков, 5,8 ГБ. Это больше всей памяти Docker (4 ГБ),
> поэтому база не может держать всё в RAM — как в настоящей системе.
>
> **Индексы:** все 5 запросов сервиса идут по первичным ключам. Лишний индекс я проверил:
> он делает каждый лайк на 63% медленнее по p99, а ни один запрос его не использует.
>
> **Самый заметный выигрыш — sync worker:** один запрос с `unnest` вместо 1000 отдельных.
> p99 батча 44 → 23 мс.
>
> **Партиции:** `likes` по HASH(user_id) на 16 частей. Каждый запрос читает 1 часть из 16.
> RANGE по дням проверил: запрос без фильтра по дате лезет во все 31 партицию и в 2,3 раза медленнее.
> Но для удаления старых данных RANGE идеален: DROP PARTITION в 130 раз быстрее, чем DELETE.
>
> **PgBouncer:** 16 процессов приложения не влезают в лимит Postgres в 100 соединений.
> Сначала с PgBouncer стало хуже — 88% ошибок. Я нашёл по логам две причины и исправил:
> после этого 0,05% ошибок.
>
> **Реплика:** чтения ушли с основной базы, p99 чтений 173 → 50 мс. Лаг реплики максимум 0,6 с,
> а требование ≤ 2 с.
>
> **Честно:** тюнинг конфига на одном ноутбуке почти не ускорил отдельные запросы — таблицы
> всё равно больше памяти, а реплика делит с основной базой один процессор.

## Каждое изменение: что → цифра → почему

| Что сделали | Цифра | Почему так |
|---|---|---|
| Sync worker: `unnest` вместо `executemany` | p99 44 → 23 мс | 1 запрос = 1 разбор и 1 план. 1000 запросов = 1000 раз то же самое |
| PgBouncer | без него `too many clients` при 8 процессах | реальных соединений к базе максимум 40, сколько бы процессов ни было |
| `reset` в asyncpg выключен | ошибки 88% → 0,05% | asyncpg после каждого запроса слал «сброс» = вторая транзакция = 2 слота PgBouncer вместо 1 |
| `client_connection_check_interval` | убрали 84 «зомби»-соединения | процесс Postgres замечает, что клиент ушёл, и сам завершается |
| Реплика | p99 чтений 173 → 50 мс | чтения не конкурируют с записью на одной базе |
| Партиции HASH(user_id) | 1 из 16 партиций на запрос | во всех запросах есть `user_id = $1` → Postgres сразу знает, в какую часть смотреть |
| `fillfactor = 80` | HOT стало хуже (99 → 65%) | из-за `hot_standby_feedback = on` на реплике primary не может чистить старые версии строк |
| Конфиг (кэш 384 МБ и т.д.) | без заметного выигрыша | данные 5,8 ГБ всё равно не влезают; Postgres ещё и кэш ОС использует |

## Слова, которые надо уметь объяснить

- **EXPLAIN ANALYZE** — показывает, КАК база выполнила запрос: каким индексом, сколько строк,
  сколько времени. `Buffers: hit=230 read=273` → 230 страниц из памяти, 273 с диска.
- **Index Only Scan** — ответ целиком из индекса, таблицу даже не читали. Так работает
  `liked_by_me`: и `user_id`, и `post_id` есть в первичном ключе.
- **Partition pruning** — Postgres выкидывает партиции, где точно нет нужных строк.
  В плане видно: `on likes_p12` — только одна партиция.
- **HOT update** (Heap-Only Tuple) — если новая версия строки помещается на ту же страницу
  и меняется НЕ индексированное поле, индекс не трогается. Дешевле и меньше WAL.
- **fillfactor = 80** — оставлять 20% страницы пустыми, чтобы было место для HOT.
- **WAL** — журнал всех изменений. Пишется на диск при каждом коммите и отправляется на реплику.
- **Transaction pooling** — PgBouncer даёт реальное соединение только на время одной транзакции.
- **Replication lag** — на сколько реплика отстаёт от основной базы.
- **Watermark** — «дай всё, что изменилось после времени X» (`WHERE updated_at > X`).
- **Флаг** — пометить запись как изменённую в момент изменения (у нас `SADD dirty_posts`).

## 12 вероятных вопросов

**1. Почему вы не добавили больше индексов?**
Все запросы уже идут по первичным ключам. Лишний индекс — это минус на каждой записи:
я измерил, `likes(post_id)` даёт +63% к p99 вставки лайка.

**2. Какой запрос самый медленный и почему его нельзя ускорить индексом?**
Чтение 100 случайных постов из 50 млн (p99 159 мс). Он уже идёт по индексу, но 100 строк лежат
на ~100 разных страницах, и большинство надо читать с диска. Решение не в базе: живые
счётчики хранятся в Redis, а сюда мы приходим, только если ключа в Redis нет.

**3. Почему партиции по HASH(user_id), а не по дате?**
Во всех наших запросах к `likes` есть `user_id`, а даты нет. HASH(user_id) → 1 партиция на запрос.
По дням → все 31 партиция, в 2,3 раза медленнее.

**4. Зачем вообще партиции, если быстрее не стало?**
Для обслуживания растущей таблицы: VACUUM, перестройка индексов, ANALYZE идут по маленьким
частям, а не по одной огромной таблице.

**5. Почему `post_counters` не партиционирована?**
Запрос берёт 100 случайных постов сразу, с партициями он полез бы во все. И таблица фиксированного
размера (1 строка на пост), удалять из неё нечего.

**6. DELETE или DROP PARTITION?**
DROP: 9 мс против 1 131 мс, WAL 0,06 МБ против 21,8 МБ. DELETE трогает каждую строку,
пишет каждую в WAL и оставляет мусор для VACUUM. DROP просто удаляет файл.

**7. Зачем PgBouncer?**
У Postgres каждое соединение — отдельный процесс, лимит 100. 8 процессов × 2 API × 10 = 160.
PgBouncer держит максимум 40 реальных соединений и раздаёт их на время транзакции.

**8. Что пошло не так с PgBouncer?**
Две вещи: (1) asyncpg после каждого запроса делал «сброс» соединения → двойная нагрузка на пул;
(2) когда клиент обрывал запрос, процесс в Postgres продолжал жить и занимал слот («зомби»).
Исправил: выключил сброс, включил `client_connection_check_interval`, поставил `max_db_connections`.

**9. Не нарушает ли реплика консистентность?**
Реплика отстаёт максимум на 0,6 с (мерили под перегрузкой), требование ≤ 2 с. Пользователь может
на долю секунды не увидеть свой лайк в `liked_by_me` — для счётчика лайков это допустимо.

**10. Почему sync worker использует флаг, а не watermark?**
Watermark без индекса = полный проход по 50 млн строк (2,3 с). С индексом на `updated_at` каждое
обновление меняет индекс → HOT 100% → 0%, WAL +45%. Флаг стоит один `SADD` в Redis.

**11. Почему `synchronous_commit = off` в sync worker — это безопасно?**
`post_counters` — копия, живые значения в Redis. Если Postgres упадёт, потеряем последние
~0,6 с копии, и следующая синхронизация запишет их снова. Для лайков (`likes`) — не выключали.

**12. Почему тюнинг конфига почти ничего не дал?**
Данные 5,8 ГБ, а памяти 4 ГБ на всё — ни 128, ни 384 МБ кэша не меняют картину. Плюс реплика на
том же ноутбуке забирает CPU и диск. На отдельных серверах эффект был бы другим.

## Показать вживую в терминале

```bash
# 0. Поднять «после» (если не запущено)
docker compose -f docker-compose.yml -f docker-compose.db.yml up -d

# 1. Сколько данных
docker compose exec postgres psql -U postgres -d counters -c "
  SELECT relname, n_live_tup, pg_size_pretty(pg_total_relation_size(relid))
  FROM pg_stat_user_tables ORDER BY n_live_tup DESC LIMIT 5;"

# 2. Partition pruning: запрос читает 1 партицию из 16
docker compose exec postgres psql -U postgres -d counters -c "
  EXPLAIN (ANALYZE, BUFFERS) SELECT post_id FROM likes WHERE user_id = 12345 AND post_id = ANY('{1,2,3}');"

# 3. Самый медленный запрос: 100 случайных постов (смотри Buffers read=...)
docker compose exec postgres psql -U postgres -d counters -c "
  EXPLAIN (ANALYZE, BUFFERS) SELECT post_id, likes, views FROM post_counters
  WHERE post_id = ANY(ARRAY(SELECT (g * 2654435761 % 50000000) + 1 FROM generate_series(1,100) g));"

# 4. PgBouncer: клиентских соединений много, реальных — мало
docker compose -f docker-compose.yml -f docker-compose.db.yml exec pgbouncer \
  psql -h 127.0.0.1 -p 6432 -U postgres pgbouncer -c "SHOW POOLS;"

# 5. Реплика и её лаг
docker compose exec postgres psql -U postgres -c "
  SELECT client_addr, state, replay_lag FROM pg_stat_replication;"

# 6. HOT-апдейты
docker compose exec postgres psql -U postgres -d counters -c "
  SELECT relname, n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'post_counters';"

# 7. Итоговая таблица «до / после» прямых SQL
cat benchmark/db_results.md
```
